# Resource authority gate — implementation proposal

**Status: design only; no resource grants or new privileged APIs exist.** This is a narrow successor to the SQLite schema-3/v1-layout, controller, and registered-plugin recovery-hold increments. It does not authorize deployment or use of owner resources for testing. The dependency ordering in `docs/ORBIT_EVOLUTION_PLAN.md` (steps 5–6), `docs/adr/001-evolution-boundaries.md`, `docs/RECOVERY.md`, and `docs/PLUGINS.md` takes precedence over older historical status paragraphs in `docs/ORBIT_EVOLUTION_AUDIT.md`, `docs/ORBIT_EVOLUTION_HANDOFF.md`, and the broad `docs/ROADMAP.md`.

## Present authority is not a resource grant

`server/workspace.mjs`/`scripts/workspace_control.py` offer revision-checked layout/controller mutations with a workspace-scoped capability, distinct from owner browser token/origin authentication. `server/sqlite-workspace-store.mjs` stores transactional revisions, checkpoints, keyed receipts and metadata outbox in schema 3; `contracts/workspace-v1.mjs` still describes layout v1. Pane IDs persist across layout moves, but a pane is a **placement/display handle**, not consent to its shell, browser, native app or backing data. A plugin ID/version is an app identity, not a resource identity or permission. The owner token currently confers broad trusted UI access; a controller capability authorizes layout commands, not reading terminal output or controlling a shared browser. Neither should be implicitly upgraded to a broker grant.

Current relevant routes are heterogeneous, not one broker:

| Surface | Existing observation/control and actual boundary |
| --- | --- |
| Host terminal | `server/index.mjs:server.on('upgrade')` authenticates `/api/terminal` WebSocket with owner token/origin; its `auth`, `input`, `resize`, `ack`, `history` message handling opens an interactive PTY, transports output and requests history. `server/local-host.mjs:LocalHostProvider.spawn` attaches valid pane IDs to `pane-<id>` tmux sessions; `captureHistory` reads pane and alternate-screen history. `src/panes.ts:open` connects xterm. This is **not** a read-only observation API: the server does not establish workspace ownership of a supplied syntactically valid pane ID, and terminal history is not layout state. Do not retrofit broad history onto controller capability. |
| Shared Chromium | Owner-token/origin-protected `server/agent.mjs:createAgentHandler` actions `shared_browser_connection` and `connection_password` supply viewer details/allowlisted password, not per-tab consent. `src/shared-browser.ts:mountSharedBrowser` embeds noVNC; `scripts/shared_browser.py` accesses local CDP directly for tabs, text, screenshots, navigation, click, fill and key. That CLI is a separate trusted-host authority; a viewer placement is not a CDP grant. |
| Shared desktop/native apps | `scripts/shared_desktop.py` uses direct container/X11 operations for window listing, screenshot, click, key, type and allowlisted launch. `src/xpra-apps.ts:xpraApps` and `src/linux-app-url.ts:linuxAppUrl` address fixed Xpra viewers; `server/agent.mjs:connection_password` supplies authenticated viewer credential. Separate password-protected viewers share focus; there is no inspected Orbit server route granting exact native-window pixels or input by workspace. See `docs/SHARED_DESKTOP.md` and `docs/XPRA_APPS.md`. |
| Workspace metadata | `server/index.mjs` routes workspace, control, recovery and events separately. `server/workspace.mjs:handle` checks browser owner token/origin versus controller workspace capability; `server/workspace-events.mjs:handle` pages bounded metadata, not resource payload. `scripts/workspace_control.py:request` uses the private loopback projection; this is not terminal/CDP/VNC/Xpra authorization. |

Even today's owner-token terminal read/interactive route is not a safe template for a narrower agent/plugin observation service. The proposed gate must check a verified resource binding in addition to authenticating its caller, rather than relying on client-provided pane identity.

The independent registered-plugin hold in `server/workspace.mjs`, `server/sqlite-workspace-store.mjs` and `public/recovery.js` is an owner-only, persistent policy outside checkpoints. It prevents *registered-plugin activation* via committed state while held and fences old command receipts by policy generation; it is **not** a general safe boot, private-data revocation, disconnected-frame kill switch, terminal gate or external-service shutdown (`docs/RECOVERY.md`, `docs/adr/005-registered-plugin-recovery-hold.md`). Static `/apps/` content and cached frames remain reachable. `src/plugins.ts` and `docs/PLUGINS.md` describe sandboxed app lifecycle with no general privileged host bridge, but its current app CSP allows network access; the exceptional reviewed one-way `src/tool-feed.ts:bindToolFeed` metadata integration (two pinned entry paths in source) is not a general permission mechanism. Its `broadcast` uses a wildcard destination and module-global history/sinks; it must not be extended to private payloads. Do not hand a plugin private bytes merely because it is sandboxed.

## Proposed identity and policy model

Keep three different keys: (1) a stable **resource descriptor** `(workspace_id, provider, opaque_resource_id, incarnation)` assigned by the trusted provider (for example an exact tmux-backed shell/session or managed browser tab), with provider status available/unavailable; (2) one or more **placements** referring to it, potentially absent, moved, split, closed or recreated; and (3) an independent **grant** `(grant_id, subject, resource_key, operation, scope, expiry, generation, state)` held outside v1 layout/checkpoints. Pane ID can seed a legacy mapping only after verifying provider binding; it must not be treated as proof that an old or newly recycled pane owns the same process. Unknown providers stay unavailable descriptors rather than being deleted or granted implicitly. A plugin hash, agent/controller actor or trusted integration must have an explicit subject identity; a workspace-wide wildcard is not a first-slice resource scope.

A trusted provider must prove the binding without causing a side effect: existing `LocalHostProvider.spawn` uses tmux `new-session -A`, so a missing shell must **not** be created while selecting or observing it. Exit/recreation under the same `pane-<id>` name changes incarnation. A copied/retyped/restored pane, foreign workspace ID, closed or navigated browser target, missing provider, or detached resource fails closed until re-resolved; whether detaching should revoke is an explicit owner-policy decision, not an implicit layout consequence. If future delivery reaches plugins, bind the subject to exact reviewed bundle hash *and* current frame activation/channel, invalidating on update, navigation, backend substitution, disable or removal.

The first permission should be **read-only, exact-resource, bounded observation**, denied by default. Example conceptual request: an owner-selected *one terminal's* bounded recent output, or *one managed browser tab's* URL/title after a reviewed provider is available; no terminal input, browser click/fill/navigate, native keyboard/mouse, bulk history, arbitrary URL, cross-resource enumeration or DOM/screenshot in this slice. Selecting a pane in layout cannot authorize its resource; the owner must see subject, exact target, fields, byte/time limits, destination and consequences, then consent through owner-authenticated UI. The controller cannot self-grant with its workspace capability. No remembered or permanent consent by default. The read checks an unexpired active grant at request time and again before delivery, applies a finite byte/record/time bound, and never accepts a grant ID as a bearer secret in place of normal authentication. Return a generic unavailable/denied result rather than leaking existence through provider details where feasible.

Grant decisions must be serialized with their own monotonically increasing **authority generation**; revoke marks grants inactive and increments generation transactionally. Every observation carries the generation observed at authorization, and the broker rechecks the same current generation, grant, subject, target incarnation and expiry immediately before delivery. Queue and provider callbacks carry a short request identity and deadline; a revocation or expiry cancels queued work and discards results that arrive later. Define a linearization point for the final delivery decision versus revocation commit (for example, a short serialized decision and bounded single buffered response), rather than claiming that an arbitrary network write is atomic with SQLite. Bytes already released into the socket or delivered before revocation cannot be clawed back; disclose this temporal limit. Chunked responses would require per-chunk fencing and are **not** admitted in the first slice. A read authorized after revocation is denied; an already released read is logged as released, not retroactively erased. A provider disappearing/restarting invalidates its incarnation, not just its placement.

Grant ledger, generation and revocation tombstones live outside layout undo; do **not** serialize them in `workspace state`, plugin config, pane URL or checkpoint. `restore`, old sync snapshots, plugin enable/update and command-receipt replay cannot mint, restore or bypass grants. A restored placement referencing an old resource receives no authority. A database backup containing a grant ledger is a *security-state backup*, not a safe layout rollback: restoring an old backup after a later revocation risks resurrection unless the design uses an independent monotonic epoch/high-water revocation record and refuses older policy snapshots, or mandates explicit all-grants-revoked quarantine after restore. Prefer default quarantine on administrative restore until owner reviews exact resources; this choice needs a tested operational procedure. The current registered-plugin hold's generation fencing is a useful pattern, **not** proof that grants inherit it automatically.

## Threat boundary and information flow

This is a local single-owner system, not multi-user process isolation. A malicious same-UID host process, owner shell, trusted source edit, compromised server, or holder of the owner token is outside the prospective sandbox guarantee. Browser pages, shell output/history, file names and native application content are **untrusted data**, including apparent instructions to Hermes; no observation text should become privileged instructions. The tmux shell persists outside its viewer; closing a pane or restoring a checkpoint does not terminate a process or erase output. Remote websites, shared-browser CDP and native app containers have separate credentials, focus and network boundaries; a grant for one must not silently confer another.

Audit **metadata** separately from sensitive payload: append actor/subject, opaque resource ID (redacted in broadly visible views), operation, grant/generation, decision, timestamps, bounded counts, revoke/expiry/delivery status and fixed error category to a private, access-controlled audit ledger. Track authorized, capture completed, release attempted and recipient acknowledged as distinct outcomes; an outbox commit cannot prove receipt. Denials need their own bounded, flood-resistant audit path, not a success event rolled back with the request. Never put output, URLs/titles (including query secrets), DOM text, screenshots, terminal history, selectors, cookie values, credentials, arbitrary provider errors, model prompts or user-authored intent in workspace metadata outbox/event pages or ordinary diagnostic logs. `server/sqlite-workspace-store.mjs:commit` persists full command `result_json`/`record_json` in receipts; **do not** route observations through this general receipt path or its replayable response. If payload retention is required later, specify a separate encrypted/private store with retention and access policy; first slice retains no observation body server-side. Existing workspace events are metadata delivery, not a private stream.

**Egress is a prerequisite, not a follow-up checkbox:** current sandboxed apps allow network access; native containers and shared Chromium also have outbound paths, and Hermes/model tool endpoints may send data externally. Until network destinations and routing are constrained and tested (or private bytes stay exclusively in a trusted owner-only view), do not expose terminal/browser/native private observations to plugin frames or model endpoints. A future sandbox profile must cover fetch, scripts, images/styles/fonts, forms, frames, navigation, redirects, popups/downloads and supported browser channels, not just one CSP directive. A permission prompt cannot undo exfiltration once data is delivered. Do not add generic postMessage, local proxy, fetch, clipboard, model-tool or app-storage bridges as part of this slice.

## Narrow implementation candidate (not yet implemented)

1. Specify a read-only provider registry and typed exact-resource descriptors; bind a terminal descriptor to its verified tmux session incarnation, not just a pane or title. Define an owner-only resource selector that does not enumerate private content to a controller/plugin. Choose **one bounded terminal output snapshot** to trusted owner UI as the first provider; browser metadata is the next distinct adapter only after proving revocable exact tab/document identity. Snapshot size, tmux capture timeout, terminal escape handling and no-implicit-create behavior are part of the contract. This is not full terminal history access.
2. Add a separate grant/revocation ledger and monotonic workspace authority generation to a **new** SQLite schema migration, with an owner-visible minimal grant/revoke/status inspector. Validate strict contracts and bounded payloads before provider access. Owner-authenticated create/revoke commands use explicit confirmation and idempotency; observations authenticate subject, exact operation/resource and current generation. Persist decision metadata, never the observation response in generic receipts. Do not hold a SQLite write transaction while awaiting tmux/CDP/network work. Define retry semantics for revoked/expired old grant-command receipts before implementing.
3. First expose a private, authenticated owner-only bounded read path for a *single* exact resource with no plugin/model forwarding. Explicit owner consent, finite grant lifetime, cancellation, authorization before capture and a fenced final release are required. Only after isolated end-to-end tests and egress controls consider delivery to sandbox apps or agents. Never make generic terminal input/history or browser/native control endpoints as a shortcut.

No normalized v2 layout migration, per-project roles, durable plugin data store, broad browser automation broker, arbitrary backend execution, persistent job lease, model egress gateway or network sandbox is designed here. The terminal and shared/native surfaces may need provider work before even this read-only slice is feasible; do not claim capability from a mock provider.

### Upgrade and rollback obligations

Schema 3 is the present baseline and layout remains v1. A schema bump must refuse older binaries/writers; stop all writers for migration with explicit shell/session preservation planning (no restart authorized by this proposal). Migration creates zero active grants, records the new epoch/generation, validates provider descriptors, and retains previous state/checkpoints/receipts intact. Ordinary restart must preserve current revocations. Existing legacy exports cannot encode grants; deny export or mark an offline export irrevocably grant-free and require a quarantined new runtime. DB backup/restore must explicitly preserve or invalidate policy and test stale-backup behavior; a generation restored from the same old backup is **not** an independent high-water mark. On administrative restore, prefer broker-disabled, zero-active-grants quarantine and a new runtime authority epoch invalidating old channels until fresh owner authorization; if seamless restoration is required, implement a separate anti-rollback authority. A simple copied SQLite file is neither a live backup nor a revocation guarantee. Keep old binaries off migrated runtime and test migration crash/rollback plus newer-schema refusal. If the feature is rolled back, disable the read endpoint first, invalidate grants and do not revive them through a schema downgrade.

### Acceptance matrix for a future implementation

| Scenario | Required outcome |
| --- | --- |
| No grant, wrong subject/operation/workspace/resource/incarnation, expired grant | No bytes; bounded generic denial; no provider read side effect |
| Owner consent / controller attempts grant / malformed payload | Explicit owner confirmation succeeds only for exact target and scope; controller denied; strict schema/size checks |
| Placement move, split, close, recreation and plugin lifecycle | Existing resource identity stable only when provider says same incarnation; no placement creates consent |
| Revoke racing queued, in-provider and buffered read; provider restart | No read authorized after revoke; stale buffered result discarded; released socket bytes documented as irretrievable; old incarnation fenced; streaming rejected |
| Layout checkpoint restore, old sync, old receipt replay, plugin hold/release | No grant resurrection; hold remains separately enforced; activation is not authorization |
| SQLite restart, concurrent writers, migration/restore/old binary | Generation monotonic; stale backup quarantined; no mixed writers; no grant activation by schema upgrade |
| Logs, receipts, outbox, exports, audit access | Decision metadata only; no payload in generic receipts or events, no sensitive body/credential/URL/selector; private audit and denial retention bounded |
| App/model egress and disconnected viewer | Private bytes never forwarded without independently tested egress policy; revocation cannot reclaim already delivered data |

Tests need disposable SQLite/runtime and provider fixtures, focused real-server owner/controller/auth failures and browser owner-consent/revoke inspection in a separate test workspace. Extend `tests/recovery-policy.test.mjs`, `tests/recovery-policy-storage.test.mjs`, `tests/workspace-receipts.test.mjs` and SQLite contention/backup/migration patterns; the indispensable new case races **actual asynchronous capture and release** with revoke, including provider failure, timeout, oversized output and a late completion after cancellation. Later plugin-gate tests must cover changed bundle, frame navigation, forged channel and attempted egress. Run `npm run check`, relevant publisher/isolated browser checks for executable changes; no build or browser claim is made by this design-only document.

## Decisions before implementation

- Which **single** provider/field set is the first real bounded observation (terminal output has ANSI/control/secret issues; browser metadata URLs may contain secrets)? Is there a viable non-sensitive first target?
- Where does the monotonic revocation high-water mark survive an *older* SQLite backup restored as a new runtime? Choose external authority epoch or fail-closed all-grants quarantine; define disaster-recovery owner workflow.
- How are subjects authenticated independently of plugin IDs or controller capability, and how are owner UI consent and provider incarnation established without leaks or ID reuse?
- What egress isolation is enforceable for sandbox apps and Hermes/model destinations before any future private-data delivery? This proposal intentionally leaves that gate closed.
