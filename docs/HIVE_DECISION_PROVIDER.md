# Can Hive submit the owner’s answer?

**No.** Hive can show a reported owner question, inspect its evidence and identify what the owner would need to decide it. Its `snapshot/1:decisions` row has no executable target. BundleBees has several real decision writers; none of the inspected interfaces accepts this row as an authenticated, revision-bound request and returns proof of its intended effect. No writer, proxy, command, decision deep link or signer is registered here.

## What the inspector establishes

| Evidence in this observation | What it supports |
| --- | --- |
| Unique public request ID, reviewed question or fallback title, state, source and observation time | The queue reported a request. Only a current, uniquely matched `pending` record is an owner inbox item. Different questions remain separate even when they name the same job. Interruption makes current status unknown. |
| Typed public job ID, when provided | The request names that job. A source-approved subject may also be visible without a job binding. A similar title, repository, stage or nearby timestamp supplies no binding. |
| Pipeline base revision; PR branch or CI status; verifier result on a specific revision | None supplies the **current candidate head and frozen contract of this request**. A changed head needs a new comparison. Confirmed test results concern the named suite/run only. A failed check does not establish that review is pending. |
| `decided`, `applied`, or an applied timestamp | A reported queue transition. Neither an authenticated owner's acceptance nor proof that a merge, dispatch, budget change or deployment happened. Current lease/fence, remaining budget, allowed options, owner authority and effect receipt stay **Unknown**. A separate report about a job is not a signed preview for a request. |
| Section or run time in the timeline | Time of a source record or collection. The timeline does not manufacture a start, recovery or completion. A retryable flag, fallback route or later disappearance from the bounded list cannot confirm recovery. |

**Next investigation:** use the public ID to locate the sealed request in the originating system; compare its digest, subject and current revision with the evidence the owner actually reviewed. Seek a distinct consumption/effect receipt. Never send a secret, nonce or signed envelope into Hive to fill an unknown cell.

## Exact missing gates for a separate lead review

1. **Identity and scope:** an installed, version-verified owner-decision provider with a unique sealed request lookup for the exact enrolled workspace, coordinator, request namespace, kind and subject. Neither a public selector nor sharing a read-only report enrolls such a provider.
2. **Authenticated owner intent:** a trusted, separately granted owner surface with the permitted responses and their specific effects, an exact preview digest, expiry and deliberate confirmation. Credentials, private evidence, signatures and nonces must stay outside the pane. A chat reply, role label, callback or queue count is not consent.
3. **Fresh state and fences:** compare the live request/subject, current contract and candidate head at confirmation and consumption, plus the applicable authorization, lease/fence, remaining budget and downstream preconditions. Refuse ambiguity, altered scope/head, revocation, expiry and superseded or already-consumed requests.
4. **Durability and reconciliation:** an idempotent consumer for *this* decision kind, conflict refusal, a durable signed owner-decision receipt and a **separate, verifiable scoped effect receipt**. An HTTP success, queued intent or `applied_at` alone is insufficient. On timeout, disconnect, stale head or missing receipt the result is unknown; read back by stable identity rather than issuing another write.

Only after all four gates are evidenced together for the same deployed provider should a separate lead review consider any action integration. This inspection used Git and GitHub read endpoints only; it did not exercise a decision endpoint or alter coordinator state.
