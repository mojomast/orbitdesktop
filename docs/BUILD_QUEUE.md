# Automated build queue

Open Hermes tools → Automated build queue in a chat pane after loading the new frontend once. This is trusted parent UI, not a privileged bridge for sandboxed plugins.

Export the old Workshop board BEFORE refreshing. In the new panel, Import Workshop board copies only tasks marked Queued. The legacy board is unchanged; imports do not preserve its evidence checkboxes or synchronize back to it. Imported evidence text becomes owner notes. Importing adds tasks and requires confirmation; it does not execute them. Review imported tasks before Start queue. Import is sequential, not atomic: if it fails midway, already-added tasks remain; review before retrying to avoid duplicate imports.

Tasks are saved to owner-only `.runtime/build-queue/queue.json`, never public app files. Start queue explicitly authorizes sequential execution through the existing authenticated Hermes Runs API. New tasks added while enabled can execute immediately. Pausing prevents the next submission; Stop task requests cancellation of the active run without undoing past actions. Approval review shows upstream command/reason and supports allow once or deny, never persistent approval. A request needing clarification or lacking the completion marker blocks advancement. The marker is Hermes's completion report, not independent proof; read result evidence.

The server worker continues while the panel/browser is closed. Restart loads the queue paused when the integration is next opened, retaining run IDs and monitoring them. An interrupted submission with unknown outcome is blocked rather than automatically replayed. HTTP 429 leaves the task queued and pauses; Start retries explicitly. A single server process owns the queue file. Run state is polled every three seconds; UI every four seconds. Queue revision checks reject stale edits. A queue may contain up to 200 records. Records from other workspaces are not displayed and pending work in another workspace prevents Start. Queue data and file effects are outside workspace checkpoints.

This addition needs a backend service restart and frontend reload. Check `/api/health` sessions before restart; do not silently interrupt host terminals. Normal workspace changes and generated plugin updates still use their documented lifecycle. No plugin tokens or host bridge were introduced.

Verification: `npm run check`; `tests/build-queue.test.mjs` tests serialization, busy/unknown submission handling, approvals, stop, persistence and stale revisions with an explicitly mocked upstream. `tests/build-queue.browser.py` uses a separate live browser workspace, saves/reloads a task, starts a real read-only Hermes terminal request, inspects returned completion evidence, and removes the test task. It reports a genuine 429 if busy rather than fabricating successful execution. Existing owner plugin bundles and board state are untouched. Backend and frontend source rollback is separate from workspace checkpoint restoration.
